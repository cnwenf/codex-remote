# 用户消息缺失：根因与修复

本记录包含已复现的机制与对应源码修复，不代表已完成 Android/iPhone 原生验收或已发布。尚未取得用户指定缺失消息的精确实例，不能将源码复现直接等同于该次现场根因。

## 实时去重把相同内容当作相同身份

原 `src/protocol/thread-store.ts` 的 `findRecentConfirmedUserMessage` 在两条消息都没有 `clientMessageId` 时，允许以标准化正文相同为依据，删除旧消息并插入新消息。

用实际 reducer 输入不同 item ID 的两次“继续”，结果只保留后一条；不同正文则保留两条。中间只有工具时也会误合并。同文但带不同图片、甚至两条纯图片消息，也可能合为一条并混合图片 ID。

修复后的身份规则：

- 同 item ID 的事件更新原消息；跨 ID 的已确认消息仅以明确共享的 `clientMessageId` 合并，不以正文合并。
- 待确认消息优先按 `clientMessageId` 确认；两边明确给出不同 ID 时禁止正文回退。
- 缺少身份元数据时，只允许正文相符、图片兼容且候选唯一的回退。多个无法区分的同文待确认项保留，不猜测删除其中一个。
- 已确认同 item ID 的原样重播不能消耗后来发出的同文待确认消息。
- 同轮确认只替换消息身份，保留原有位置，不因晚到的确认跳到工具或另一条提问后面。
- 实时与历史恢复共用图片兼容规则，已知不同图片不能互相确认。
- 排队转引导也遵循明确身份优先：确认事件带 ID 时不能回退正文匹配，避免同一确认的重播删除另一条同文排队消息。

## 历史分页把中途上下文误标为完整轮次

原 `src/gateway/desktop-state.ts` 将窗口中首次出现的 `turn_context` 当成轮次起点，并设置 `completeFromTurnStart=true`。但同一轮可能中途再次出现 `turn_context`；较大的工具记录把真正的提问隔在更早的分页中。

本机真实历史分页已观察到：同一轮前面的页只有助手/工具，继续读取较早页才出现用户提问；中间页却被标记为完整轮次。

`src/web/state/conversation-history.ts` 又使用该完整标记允许按同文替换已确认消息。构造“第一条提问 → 大日志 → 同轮 turn_context → 第二条同文提问”，尾页恢复会把第一条误合并；撤掉错误完整标记则两条保留。

现在仅 `task_started` 作为可信轮次起点；`turn_context` 仍提供轮次归属，但不证明完整前缀。读到文件开头且轮数没有超过页面上限时，包含前置上下文，避免多出空的历史页。读取仍有字节上限，不为补齐轮次无界扫描大日志。

保留真正完整前缀下的实时/落盘消息表示匹配：两侧 item ID 本来就可能不同，全面删除该兼容逻辑会产生重复气泡。必须区分“历史尚未加载到提问”与“已加载消息被错误去重删除”。

另补旧格式记录的边界：片段开头的消息可能没有逐项轮次 ID。原解析在遇到上下文时直接清空这些待归属项，使中间回复和用户提问都可能消失。现在上下文只提供候选轮次，后续带明确相同轮次 ID 的完成事件才恢复此前的消息，并保留前后顺序；遇到新轮开始或不同轮次上下文则不跨轮携带。此兼容依赖正常的新轮开始事件，不能从缺损日志中强行猜测归属。

## 回归边界

- reducer：同文独立发送、只有工具间隔、不同图片/纯图片、明确身份重播、ID 冲突、唯一与歧义待确认项。
- history hydration：ID 冲突不误删、两条同文待确认项不猜测、明确 ID 精确确认、不同图片匹配各自发送。
- queue promotion：同一 client ID 的实时/落盘双重确认只移除对应发送，不删除另一条同文消息。
- gateway 到 hydration：临时真实 JSONL/SQLite 夹具，构造“第一条提问 → 大日志 → 中间回复与补充提问 → 同轮上下文 → 第二条同文提问 → 最终回复”，分别覆盖有/无逐项轮次 ID，验证尾页与向前分页恢复均保留用户与助手消息；前缀完整标记、消息顺序与游标正确，下一轮边界不串轮。
- 原有 hook、消息流水线和 Web 桌面/移动尺寸回归继续执行。Web 的图片上传测试不等于 Android 原生上传链路已通过。

- 新增失败用例先复现，再验证修复：同文身份误合并、历史错误完整标记、旧格式上下文前缀丢失、晚到确认改变顺序、重复队列确认误删。
