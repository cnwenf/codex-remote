# 原生图片上传：超时与取消

## 已确认的缺陷

上传分为 WebView 读取图片、分块写入原生缓存、原生 HTTP 上传三个阶段，图片全部上传成功后才启动或引导对话。连接列表的绿色状态只验证了状态查询，不代表这三个阶段都成功。

- 原来的超时处理会等待 `cancelImageUpload`。如果桥接本身卡住，取消也不返回，上传 Promise 就一直不结束，发送状态不能恢复。
- 原生缓存创建在超时之后才返回时，原来的清理已经结束，漏掉迟到的缓存文件。
- `FileReader` 只处理成功和错误，不处理中止，文件读取中止后会一直等到总超时。
- Android 的 `claim` 提前移除了上传管理记录。网络上传开始后，取消不能再找到临时文件，也没有对应 HTTP 连接可以断开。
- Android 只配置了连接和响应读取超时，没有覆盖阻塞写入；WebView 暂停时，JavaScript 超时也不能充当可靠的原生清理机制。

这些是源码及针对性回归确认的缺陷；没有设备日志，不能据此断言用户本次首次超时具体发生在哪个阶段。

## 修复边界

- `src/mobile/native-image-upload.ts` 集中处理上传生命周期，页面只负责装配上传入口。
- 总超时仍为 60 秒，不增加自动重试，也不改变分块大小、上传接口、鉴权方式或文件限制。
- 失败反馈不等待原生取消；读取中止立即返回；迟到回调不会继续发送，也不会影响下一次上传。
- 超时提示区分准备、读取、缓存写入和服务端传输，不记录 token、图片内容或连接地址。
- Android 保留上传所有权直到成功、失败或取消；取消使任务失效，并异步断开对应连接；原生网络阶段还有独立的 60 秒上限。

## 验证与缺口

- 前端上传用例覆盖正常分块、读取中止、清理不返回、缓存创建迟到、上传回调迟到和超时后重试。
- Java 文件生命周期用例覆盖分块/大小限制、claim 后取消、重复取消、取消先于网络挂接、成功清理、销毁后拒绝新上传和线程池关闭后的取消兜底；与上传 URL/MIME 校验合计 10 项通过。
- `pnpm check`：48 个测试文件、481 项通过；`pnpm build` 通过。
- Java 用例是在独立 JVM 上运行，不等于 Android HTTP/WebView 真机验收。完整 `:app:testDebugUnitTest` 被本机缺少 Android SDK 阻塞。
- 尚缺 Android 安装包构建、真机小图/大图/多图发送、弱网和后台恢复、发送成功后的双端图片显示验收。本次未发版、未更换正在运行的客户端。
